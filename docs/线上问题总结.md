## 1. Scanner 线程安全 — `IndexOutOfBoundsException`

### 现象

CLI 运行时偶发 `java.lang.IndexOutOfBoundsException: end`，堆栈指向 `Scanner.nextLine()`。

### 根因

4 个线程同时读取 `System.in`：

| 线程 | 用途 | 读取方式 |
|------|------|----------|
| `CLI-Main` | 主输入循环 | `Scanner.nextLine()` |
| `setupInteractivePermission` | 工具权限确认 | `Scanner.nextLine()` |
| `setupAskUserHandler` | AskUser 交互 | `Scanner.nextLine()` |
| `CancelMonitor` | Esc 中断监听 | `JLine terminal.reader()` |

`java.util.Scanner` **不是线程安全的**。多个线程并发调用 `nextLine()` 导致内部缓冲区状态错乱，抛出 `IndexOutOfBoundsException`。

### 修复

三层防御：

```
第一层：synchronized(scanner) 保护 Scanner 的所有读取
第二层：dialogActive 标志 — 弹确认框时暂停 CancelMonitor
第三层：terminalLock — JLine NonBlockingReader 和 Scanner 读写互斥
```

关键代码：

```java
// 主输入 + 确认框 统一走此方法
private String readLine() {
    synchronized (scanner) {
        try { return scanner.nextLine(); }
        catch (RuntimeException e) {
            // Scanner 损坏时自动重建
            scanner = new Scanner(System.in);
            return "";
        }
    }
}

// 确认框专用：用 JLine reader 逐字符回显，与 CancelMonitor 共享 terminalLock
private String readInteractiveLine() {
    synchronized (terminalLock) {
        NonBlockingReader reader = terminal.reader();
        // 逐字符读取 + 回显
    }
}

// CancelMonitor 检查 dialogActive + terminalLock
while (currentRequestId != null && !cancelled) {
    if (dialogActive) { Thread.sleep(100); continue; }
    int ch;
    synchronized (terminalLock) { ch = reader.read(50); }
    if (ch == 27) { ... }
}
```

### 教训

- **永远不要在多线程中共享 Scanner**
- 终端交互场景下，确认弹框和主输入循环必须互斥
- JLine `NonBlockingReader` 和 `Scanner` 同读 `System.in` 时，必须统一锁管理

## 2. 权限确认 "2"（信任）无效

### 现象

用户选择"2=之后都放行"，但后续工具调用仍弹出确认框。

### 根因（与问题 #1 连锁）

1. Scanner 被多线程破坏 → `readLine()` 返回空字符串
2. JLine `terminal.reader()` 抢先消费了 `System.in` 的输入 → Scanner 读到脏数据
3. 确认处理器的输入被 CancelMonitor 提前消耗

修复 #1 后，通过 `dialogActive` 标志 + `terminalLock` + `readInteractiveLine()` 逐字符读取，确保确认输入不被干扰。

### 教训

- 并发 bug 的根因往往是**多个组件争抢同一个资源**（这里是 System.in）
- 修复时不能只修表面（加锁），要理清所有参与方的协作时序

## 3. 工作目录始终为 nanobot-java 项目目录

### 现象

在 `D:\...\ai-mcp-gateway>` 下运行 `nanobot`，AI 的工作目录仍为 `D:\...\nanobot-java`。

### 根因（5 层连锁问题）

```
① nanobot.bat 第 19 行：
   pushd "%SCRIPT_DIR%" && java ...    ← 切换工作目录到 nanobot-java

② NanobotCliApplication.main()：
   System.getProperty("user.dir")      ← 已经是 nanobot-java

③ ConfigLoader.load()：
   自己读 YAML 文件，不认 Spring Boot --agents.defaults.workspace=...   ← CLI 参数无效

④ config.yaml（nanobot-java 根目录）：
   workspace: ".."                     ← 覆盖一切，workspace = ai-vibe-coding

⑤ ExecTool：
   ProcessBuilder 没有设 directory()  ← 命令在 JVM user.dir 下执行
```

### 修复链路

```
nanobot.bat
  └→ --workspace "%CD%"（CMD 展开时机在 pushd 之前）
      └→ NanobotCliApplication
          └→ System.setProperty("nanobot.workspace", ...)
              └→ Config.getWorkspacePath()
                  └→ ① 系统属性    ← 最高优先级
                     ② YAML 配置
              └→ ExecTool.directory(workspace)
```

关键设计决策：**用系统属性传递，而不是 Spring Boot CLI 参数**。因为 `ConfigLoader.load()` 是独立于 Spring Boot 的 YAML 加载器，不认 `--agents.defaults.workspace=...`。

### 教训

- 不同配置源的**优先级链路**必须明确文档化
- 启动脚本中的 `pushd/cd` 会改变 `user.dir`，所有依赖它的东西都会受影响
- 排查配置问题时，逐层追踪加载链，不要假设"传了参数就一定生效"

## 4. PermissionMode.DEFAULT 拒绝写工具

### 现象

AI 调用 `write_file` 时报 "Tool 'write_file' is not allowed in DEFAULT mode (isReadOnly=false)"。

### 根因

`PermissionMode.DEFAULT.allowsTool()` 直接 `return tool.isReadOnly()`，注释写"写工具后续通过交互确认"但从未实现。

```java
// 代码与注释不一致
DEFAULT {
    public boolean allowsTool(Tool tool) {
        return tool.isReadOnly();  // ← 写工具直接拒绝
    }
},
```

同时 `NanobotConfig` 中已配置 ASK 规则：

```java
ruleEngine.addRule(RuleType.ASK, "exec", null, null,
    "Shell 命令执行需要您的确认");
```

但 mode 检查（Step 4）在规则匹配（Step 3）之后执行且无条件拒绝，规则形同虚设。

### 修复

```java
if (!mode.allowsTool(tool)) {
    // DEFAULT 模式 + 有交互处理器 → 走确认流程，不直接拒绝
    if (mode == PermissionMode.DEFAULT
            && interactiveHandler != null
            && !tool.isReadOnly()) {
        boolean allowed = interactiveHandler.requestConfirmation(...);
        if (!allowed) return PermissionResult.denied(...);
        // 确认通过 → 继续执行
    } else {
        return PermissionResult.denied(...);  // 原逻辑
    }
}
```

### 教训

- **注释是谎言，代码是真相**。注释说"通过交互确认"但代码是 `return tool.isReadOnly()`
- 模式/规则/守卫三层管道中，**执行顺序决定优先级**。Step 4 应该在交互处理器可覆盖时才拒绝

## 5. PathGuard `restrictToWorkspace` 未接线

### 现象

YAML 配置 `restrictToWorkspace: false`，但 PathGuard 仍拦截工作区外的文件操作。

### 根因

```java
// 构造函数默认 true
public PathGuard(String workspace) {
    this.restrictToWorkspace = true;
}

// NanobotConfig 从未调用 setRestrictToWorkspace()
@Bean
public PathGuard pathGuard(Config config) {
    return new PathGuard(config.getWorkspacePath());
    //     ↑ 永远 restrictToWorkspace = true
}
```

### 修复

一行代码：

```java
guard.setRestrictToWorkspace(config.getTools().isRestrictToWorkspace());
```

### 教训

- 构造函数默认值 + 未接线配置 = **静默的硬编码**
- 每个配置项都应该有端到端验证：YAML → 加载 → Bean 创建 → 运行时生效

## 6. 流式标题标记未去除

### 现象

CMD 窗口显示 `### ① mcp_gateway — MCP 网关配置表`（`###` 标记符可见）。

### 根因

`render()` 方法用了 `stripHeadingMarker()` 去掉 `###`，但 `renderStreamingLine()` 只加了颜色没去掉标记符。

```java
// render() — 正确
s = BOLD + PURPLE + stripHeadingMarker(s, 3) + RESET;

// renderStreamingLine() — 漏了
s = BOLD + PURPLE + s + RESET;  // ← ### 还在
```

### 修复

`renderStreamingLine()` 同样调用 `stripHeadingMarker()`。

### 教训

- 渲染逻辑有两个路径（全量/流式）时，**行为必须一致**
- 重复代码是 bug 的温床

## 7. Unix 命令在 Windows 上失败

### 现象

AI 调用 `exec pwd` → `cmd.exe /c pwd` → `'pwd' is not recognized...`

### 根因

AI 模型（DeepSeek）常输出 Unix 风格命令。`cmd.exe` 不认识 `pwd`、`ls`、`cat` 等。

### 修复

`ExecTool` 内置转换表，仅在 Windows 平台生效：

| Unix | Windows |
|------|---------|
| `pwd` | `cd` |
| `ls` | `dir` |
| `cat` | `type` |
| `clear` | `cls` |
| `which` | `where` |
| `cp` | `copy` |
| `mv` | `move` |
| `rm` | `del` |
| `touch` | `type nul >` |
| `wc` | `find /c` |

参数原样保留（如 `ls -la` → `dir -la`）。

### 教训

- AI 模型的输出天然偏向 Unix 风格，Windows 平台必须有适配层
- 转换表要覆盖纯查看命令（`pwd`/`ls`/`cat`/`which`），破坏性命令（`rm`）让 AI 谨慎使用

## 8. Dream 记忆 JSON 解析失败

### 现象

```
Failed to parse memory response, treating as plain text:
Cannot construct instance of java.util.LinkedHashMap ...
from String value (' 工作目录')
```

### 根因

LLM 返回了字符串数组 `["工作目录", "项目路径"]` 而不是对象数组 `[{"content":"工作目录", "keywords":[...], "importance":0.8}]`。

Prompt 太弱：

```
请以 JSON 格式输出记忆条目，每个条目包含：
- content: 记忆内容
- keywords: 关键词数组
- importance: 重要性(0-1)
```

没有示例，没有约束。

### 修复

改为 **system message + 严格格式约束**：

```
你是一个记忆提取助手。从对话中提取关键信息，严格按照 JSON 数组格式输出。

## 输出格式（必须是纯 JSON 数组，不要任何其他文字）
[
  {
    "content": "记忆内容（一句话描述）",
    "keywords": ["关键词1", "关键词2"],
    "importance": 0.8
  }
]

## 规则
- 只输出 JSON 数组，不要加 ```json 标记、不要加解释文字
- 不要输出字符串数组，每个元素必须是对象    ← 直击根因
- 如果没有值得长期记忆的内容，输出空数组 []
```

### 教训

- 让 LLM 输出结构化数据时，**system message + 示例 + 负面约束** 缺一不可
- 解析失败时降级为纯文本是好的兜底策略，但应该尽量让正常路径生效

---

## 总结：类 Claude Code CLI 的并发设计原则

1. **System.in 单读者** — 所有输入流操作必须通过统一的锁保护
2. **确认弹框优先** — `dialogActive` 标志暂停后台监听，避免输入争夺
3. **配置链路透明** — 系统属性 > YAML > classpath 默认，每层优先级写入 Javadoc
4. **双渲染路径一致** — 全量渲染和流式渲染必须共用相同的格式处理逻辑
5. **平台适配前置** — 命令转换/路径转换在工具层完成，不让 AI 操心操作系统差异
6. **LLM 输出防御式解析** — 永远有 fallback，但要用强 prompt 让正常路径成为大多数
