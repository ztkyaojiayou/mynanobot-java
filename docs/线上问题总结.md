## 一、多轮对话响应错位问题（Web 端）

### 1.1 问题场景
用户在连续进行多轮对话时，前端显示的响应总是慢一步，
表现为：
- 第一轮对话正常
- 第二轮对话时，AI的回答内容与第一轮相同
- 第三轮对话时，显示的是第二轮的响应
- 以此类推，每次都显示上一轮的响应

### 1.2 问题分析

#### 1.2.1 初步分析
从后端日志可以看到：
```
Received chat request: requestId=xxx, sessionId=web-xxx, contentLength=5
Found response for session: web-xxx, content length: 32
```
后端返回的响应内容是正确的（32字符），但前端显示的是旧消息（15字符）。

#### 1.2.2 深入分析
通过前端控制台日志发现：
```
[1234567890] Received response: {status: "ok", sessionId: "...", content: "一加一等于二（2）"}
[addMessage] type: bot, content: "一加一等于二（2）"
```
前端收到的响应内容也是正确的，但显示的内容不对。

#### 1.2.3 根因定位
最终定位到问题出在消息总线的响应路由机制：

1. **并发竞争条件**：多个请求并发发送到消息总线
2. **响应匹配问题**：消息总线使用单一的出站队列（`BlockingQueue<OutboundMessage>`）
3. **会话ID匹配不精确**：虽然使用会话ID（chatId）来匹配响应，但由于并发竞争，响应被错误的请求者消费
4. **消息缓存问题**：旧的响应消息没有被正确清理，导致被重复消费

#### 1.2.4 时序问题
```
请求1 (chatId=A) ──────────────────────────────────────────────────────▶ 响应1 (chatId=A)
请求2 (chatId=A) ─────────────────▶ 响应2 (chatId=A) ─────────────────▶ 显示错误
```
请求2 在响应1到达之前就消费了响应1，导致显示错误的响应。

### 1.3 解决方案

#### 1.3.1 架构改进
采用**精确匹配**机制，使用请求ID（requestId）来确保每个请求收到正确的响应。

#### 1.3.2 具体实现

**步骤1：在 OutboundMessage 中添加 requestId 字段**

```java
// OutboundMessage.java
public class OutboundMessage {
    private final String requestId;  // 新增字段

    public Builder requestId(String requestId) {
        this.requestId = requestId;
        return this;
    }
}
```

**步骤2：修改 MessageBus，添加会话响应映射**

```java
// MessageBus.java
private final ConcurrentHashMap<String, Queue<OutboundMessage>> sessionResponses;

// 发布响应时，同时添加到会话响应映射
public void publishOutbound(OutboundMessage message) {
    outboundQueue.put(message);
    if (message.getChatId() != null) {
        sessionResponses.computeIfAbsent(message.getChatId(), k -> new LinkedList<>())
                       .offer(message);
    }
}

// 使用 requestId 精确匹配响应
public OutboundMessage waitForSessionResponse(String sessionId, String requestId,
                                             long timeout, TimeUnit unit) {
    long endTime = System.currentTimeMillis() + unit.toMillis(timeout);

    while (System.currentTimeMillis() < endTime) {
        Queue<OutboundMessage> queue = sessionResponses.get(sessionId);
        if (queue != null) {
            for (OutboundMessage msg : queue) {
                if (requestId != null && requestId.equals(msg.getRequestId())) {
                    queue.remove(msg);
                    return msg;
                }
            }
        }
        Thread.sleep(50);
    }
    return null;
}
```

**步骤3：修改 ChannelServer，传递 requestId**

```java
// ChannelServer.java
String requestId = json.has("requestId") ? json.get("requestId").asText() : UUID.randomUUID().toString();
String responseContent = waitForResponse(sessionId, requestId, 60);
```

**步骤4：修改 AgentLoop，传递 requestId**

```java
// AgentLoop.java
private TurnState doRespond(TurnContext context) {
    String requestId = null;
    if (context.getMessage().getMetadata() != null) {
        Object requestIdObj = context.getMessage().getMetadata().get("requestId");
        if (requestIdObj != null) requestId = requestIdObj.toString();
    }
    OutboundMessage response = OutboundMessage.builder()
        .channel(context.getMessage().getChannel())
        .chatId(context.getMessage().getChatId())
        .content(content)
        .requestId(requestId)
        .build();
    messageBus.publishOutbound(response);
}
```

**步骤5：前端添加请求队列**

```javascript
let requestQueue = [];
let isProcessing = false;

function processQueue() {
    if (isProcessing || requestQueue.length === 0) return;
    isProcessing = true;
    const task = requestQueue.shift();
    try {
        await task();
    } finally {
        isProcessing = false;
        processQueue();
    }
}

function sendMessage() {
    addToQueue(async () => {
        await sendMessageHTTP(content);
    });
}
```

#### 1.3.3 优化后的时序
```
请求1 (requestId=req1) ──────────────────────▶ 响应1 (requestId=req1) ─────────────────▶ 显示正确
请求2 (requestId=req2) ─────────────────▶ 响应2 (requestId=req2) ─────────────────▶ 显示正确
```

### 2.1 Scanner 线程安全 — `IndexOutOfBoundsException`

#### 2.1.1 问题场景
CLI 运行时偶发 `java.lang.IndexOutOfBoundsException: end`，堆栈指向 `Scanner.nextLine()`。

#### 2.1.2 根因分析
4 个线程同时读取 `System.in`：

| 线程 | 用途 | 读取方式 |
|------|------|----------|
| `CLI-Main` | 主输入循环 | `Scanner.nextLine()` |
| `setupInteractivePermission` | 工具权限确认 | `Scanner.nextLine()` |
| `setupAskUserHandler` | AskUser 交互 | `Scanner.nextLine()` |
| `CancelMonitor` | Esc 中断监听 | `JLine terminal.reader()` |

`java.util.Scanner` **不是线程安全的**。多个线程并发调用 `nextLine()` 导致内部缓冲区状态错乱。

#### 2.1.3 解决方案
三层防御：

```
第一层：synchronized(scanner) 保护 Scanner 的所有读取
第二层：dialogActive 标志 — 弹确认框时暂停 CancelMonitor
第三层：terminalLock — JLine NonBlockingReader 和 Scanner 读写互斥
```

```java
// 主输入 + 确认框统一走此方法
private String readLine() {
    synchronized (scanner) {
        try { return scanner.nextLine(); }
        catch (RuntimeException e) {
            scanner = new Scanner(System.in);  // 自动重建
            return "";
        }
    }
}

// 确认框专用：JLine reader 逐字符回显，与 CancelMonitor 共享 terminalLock
private String readInteractiveLine() {
    synchronized (terminalLock) {
        NonBlockingReader reader = terminal.reader();
        StringBuilder sb = new StringBuilder();
        while (true) {
            int ch = reader.read(200);
            if (ch < 0) continue;
            if (ch == '\r' || ch == '\n') break;
            sb.append((char) ch);
            System.out.print((char) ch);
            System.out.flush();
        }
        System.out.println();
        return sb.toString();
    }
}

// CancelMonitor 检查 dialogActive + terminalLock
while (currentRequestId != null && !cancelled) {
    if (dialogActive) { Thread.sleep(100); continue; }
    int ch;
    synchronized (terminalLock) { ch = reader.read(50); }
    if (ch == 27) { cancelled = true; break; }
}
```

#### 2.1.4 教训
- **永远不要在多线程中共享 Scanner**
- 终端交互场景下，确认弹框和主输入循环必须互斥
- JLine `NonBlockingReader` 和 `Scanner` 同读 `System.in` 时，必须统一锁管理

### 2.2 权限确认 "2"（信任）无效

#### 2.2.1 问题场景
用户选择"2=之后都放行"，但后续工具调用仍弹出确认框。

#### 2.2.2 根因分析（与 2.1 连锁）
1. Scanner 被多线程破坏 → `readLine()` 返回空字符串
2. JLine `terminal.reader()` 抢先消费了 `System.in` 的输入 → Scanner 读到脏数据
3. 确认处理器的输入被 CancelMonitor 提前消耗

修复 2.1 后，通过 `dialogActive` 标志 + `terminalLock` + `readInteractiveLine()` 逐字符读取，确保确认输入不被干扰。

#### 2.2.3 教训
- 并发 bug 的根因往往是**多个组件争抢同一个资源**（这里是 System.in）
- 修复时不能只修表面（加锁），要理清所有参与方的协作时序

### 2.3 工作目录始终为 nanobot-java 项目目录

#### 2.3.1 问题场景
在 `D:\...\ai-mcp-gateway>` 下运行 `nanobot`，AI 的工作目录仍为 `D:\...\nanobot-java`。

#### 2.3.2 根因分析（5 层连锁问题）

```
① nanobot.bat 第 19 行：
   pushd "%SCRIPT_DIR%" && java ...    ← 切换工作目录到 nanobot-java

② NanobotCliApplication.main()：
   System.getProperty("user.dir")      ← 已经是 nanobot-java

③ ConfigLoader.load()：
   自己读 YAML 文件，不认 Spring Boot --agents.defaults.workspace=...   ← CLI 参数无效

④ config.yaml（nanobot-java 根目录）：
   workspace: ".."                     ← 覆盖一切，workspace = ai-vibe-coding

⑤ ExecTool：
   ProcessBuilder 没有设 directory()  ← 命令在 JVM user.dir 下执行
```

#### 2.3.3 解决方案

```
nanobot.bat
  └→ --workspace "%CD%"（CMD 展开时机在 pushd 之前）
      └→ NanobotCliApplication
          └→ System.setProperty("nanobot.workspace", ...)
              └→ Config.getWorkspacePath()
                  └→ ① 系统属性    ← 最高优先级
                     ② YAML 配置
              └→ ExecTool.directory(workspace)
```

关键设计决策：**用系统属性传递，而不是 Spring Boot CLI 参数**。因为 `ConfigLoader.load()` 是独立于 Spring Boot 的 YAML 加载器，不认 `--agents.defaults.workspace=...`。

#### 2.3.4 教训
- 不同配置源的**优先级链路**必须明确文档化
- 启动脚本中的 `pushd/cd` 会改变 `user.dir`，所有依赖它的东西都会受影响
- 排查配置问题时，逐层追踪加载链，不要假设"传了参数就一定生效"

### 2.4 PermissionMode.DEFAULT 拒绝写工具

#### 2.4.1 问题场景
AI 调用 `write_file` 时报 "Tool 'write_file' is not allowed in DEFAULT mode (isReadOnly=false)"。

#### 2.4.2 根因分析
`PermissionMode.DEFAULT.allowsTool()` 直接 `return tool.isReadOnly()`，注释写"写工具后续通过交互确认"但从未实现。

```java
DEFAULT {
    public boolean allowsTool(Tool tool) {
        return tool.isReadOnly();  // ← 写工具直接拒绝，从未走交互确认
    }
},
```

同时 `NanobotConfig` 中已配置 ASK 规则（exec 工具需要确认），但 mode 检查（Step 4）在规则匹配（Step 3）之后无条件拒绝，规则形同虚设。

#### 2.4.3 解决方案

```java
if (!mode.allowsTool(tool)) {
    // DEFAULT 模式 + 有交互处理器 → 走确认流程，不直接拒绝
    if (mode == PermissionMode.DEFAULT
            && interactiveHandler != null
            && !tool.isReadOnly()) {
        boolean allowed = interactiveHandler.requestConfirmation(...);
        if (!allowed) return PermissionResult.denied(...);
        // 确认通过 → 继续执行
    } else {
        return PermissionResult.denied(...);
    }
}
```

#### 2.4.4 教训
- **注释是谎言，代码是真相**。注释说"通过交互确认"但代码是 `return tool.isReadOnly()`
- 模式/规则/守卫三层管道中，**执行顺序决定优先级**。Step 4 应该在交互处理器可覆盖时才拒绝

### 2.5 PathGuard `restrictToWorkspace` 未接线

#### 2.5.1 问题场景

- 构造函数默认值 + 未接线配置 = **静默的硬编码**

### 2.6 流式标题标记未去除

#### 2.6.1 问题场景
CMD 窗口显示 `### ① mcp_gateway — MCP 网关配置表`（`###` 标记符可见）。

#### 2.6.2 根因分析
`render()` 方法用了 `stripHeadingMarker()` 去掉 `###`，但 `renderStreamingLine()` 只加了颜色没去掉标记符。

```java
// render() — 正确
s = BOLD + PURPLE + stripHeadingMarker(s, 3) + RESET;

// renderStreamingLine() — 漏了
s = BOLD + PURPLE + s + RESET;  // ← ### 还在
```

#### 2.6.3 解决方案
`renderStreamingLine()` 同样调用 `stripHeadingMarker()`。

#### 2.6.4 教训
- 渲染逻辑有两个路径（全量/流式）时，**行为必须一致**
- 重复代码是 bug 的温床

### 2.7 Unix 命令在 Windows 上失败

#### 2.7.1 问题场景
AI 调用 `exec pwd` → `cmd.exe /c pwd` → `'pwd' is not recognized...`。AI 常输出 Unix 风格命令，`cmd.exe` 不认识。

#### 2.7.2 解决方案
`ExecTool` 内置转换表，仅在 Windows 平台生效：

| Unix | Windows | Unix | Windows |
|------|---------|------|---------|
| `pwd` | `cd` | `cp` | `copy` |
| `ls` | `dir` | `mv` | `move` |
| `cat` | `type` | `rm` | `del` |
| `clear` | `cls` | `touch` | `type nul >` |
| `which` | `where` | `wc` | `find /c` |

参数原样保留（如 `ls -la` → `dir -la`）。

#### 2.7.3 教训
- AI 模型的输出天然偏向 Unix 风格，Windows 平台必须有适配层
- 转换表要覆盖纯查看命令，破坏性命令让 AI 谨慎使用

### 2.8 Dream 记忆 JSON 解析失败

#### 2.8.1 问题场景
```
Failed to parse memory response, treating as plain text:
Cannot construct instance of java.util.LinkedHashMap ...
from String value (' 工作目录')
```

#### 2.8.2 根因分析
LLM 返回了字符串数组 `["工作目录", "项目路径"]` 而不是对象数组 `[{"content":"工作目录", "keywords":[...], "importance":0.8}]`。Prompt 太弱，没有示例和约束。

#### 2.8.3 解决方案
改为 **system message + 严格格式约束**：

```
你是一个记忆提取助手。从对话中提取关键信息，严格按照 JSON 数组格式输出。

## 输出格式（必须是纯 JSON 数组，不要任何其他文字）
[
  {
    "content": "记忆内容（一句话描述）",
    "keywords": ["关键词1", "关键词2"],
    "importance": 0.8
  }
]

## 规则
- 只输出 JSON 数组，不要加 ```json 标记、不要加解释文字
- 不要输出字符串数组，每个元素必须是对象    ← 直击根因
- 如果没有值得长期记忆的内容，输出空数组 []
```

解析失败时降级为纯文本，已有兜底。

#### 2.8.4 教训
- 让 LLM 输出结构化数据时，**system message + 示例 + 负面约束** 缺一不可

### 2.9 总结：CLI 并发设计原则

1. **System.in 单读者** — 所有输入流操作必须通过统一的锁保护
2. **确认弹框优先** — `dialogActive` 标志暂停后台监听，避免输入争夺
3. **配置链路透明** — 系统属性 > YAML > classpath 默认，每层优先级写入 Javadoc
4. **双渲染路径一致** — 全量渲染和流式渲染必须共用相同的格式处理逻辑
5. **平台适配前置** — 命令转换/路径转换在工具层完成，不让 AI 操心操作系统差异
6. **LLM 输出防御式解析** — 永远有 fallback，但要用强 prompt 让正常路径成为大多数

### 2.10 文件工具默认路径 "." 不走 PathGuard

#### 2.10.1 问题场景
AI 调用 `list_dir` 不传 path 时，列出的却是 nanobot-java 目录结构（pom.xml、src/、target/），而非当前 workspace。

#### 2.10.2 根因分析

```
① AI 调用 list_dir() 不传 path
② ListDirTool 取默认值 "."
③ ToolRegistry.applyGuards() 只在对 path 参数非空时才调 PathGuard
   → path=null → 跳过 PathGuard
④ Paths.get(".") → 基于 JVM user.dir 解析
⑤ user.dir = nanobot-java（因 pushd） → 列出错误目录
```

同时 `GlobTool` 用 `basePath` 而非 `path` 做参数名，`applyGuards()` 只查 `path` 参数，完全漏掉了 GlobTool。

#### 2.10.3 解决方案

```java
// ToolRegistry.applyGuards() — 之前
if (pathParam != null) {
    Path validatedPath = pathGuard.resolvePath(pathParam);
    securedParams.put("path", validatedPath.toString());
}

// 修复后：无论 LLM 是否传参，默认 "." 一律走 PathGuard
String pathParam = (String) params.get("path");
if (pathParam == null) pathParam = (String) params.get("basePath"); // GlobTool
Path validatedPath = pathGuard.resolvePath(pathParam != null ? pathParam : ".");
securedParams.put("path", validatedPath.toString());
if (params.containsKey("basePath")) {
    securedParams.put("basePath", validatedPath.toString());
}
```

#### 2.10.4 教训
- 工具默认值和 PathGuard 必须统一使用 workspace，不能依赖 `user.dir`
- 类似工具的参数名不一致（path vs basePath）是隐藏的坑，guard 要做兼容

### 2.11 ExecTool 无后台模式 — 长期服务被超时杀

#### 2.11.1 问题场景
AI 通过 `exec mvn spring-boot:run` 启动 Spring Boot 应用，120 秒后进程被强制终止（超时杀）。

#### 2.11.2 根因分析
`ExecTool` 只有前台模式：启动进程 → 等待退出 → 拿输出。Spring Boot 服务是阻塞运行的，永远不退。120s 超时后触发 `process.destroy()`。

#### 2.11.3 解决方案
新增 `background: true` 参数：

```
exec { command: "mvn spring-boot:run", background: true }
  │
  ├─ 启动子进程
  ├─ 采集前 3 秒启动日志
  ├─ 进程存活 → 返回 "后台进程已启动 (PID: xxx)"
  ├─ 进程已死 → 返回 exit code + 日志
  └─ 立即返回，daemon 线程持续排空 stdout/stderr
```

参考设计：Claude Code 的 Bash 工具自带 `run_in_background: true`。

#### 2.11.4 教训
- 工具设计时要区分"短期命令"和"长期服务"两种场景
- 超时策略应可配置，且长期服务应有独立模式避免误杀

### 2.12 @ 文件引用误判 git URL 为路径

#### 2.12.1 问题场景
用户输入 `git push git@github.com:ztkyaojiayou/xxx.git`，CLI 崩溃：

```
InvalidPathException: Illegal char <:> at index 10: github.com:...
  at CliChannel.resolveFilePath()
  at CliChannel.resolveFileRefs()
```

#### 2.12.2 根因分析
`@` 文件引用正则 `@(\\S+)` 无前后文限制，`git@github.com:...` 中的 `@github.com:...` 被当成文件路径。`Paths.get("github.com:...")` 在 Windows 上因 `:` 非法字符抛出异常，导致主线程崩溃。

#### 2.12.3 解决方案
正则加负向前瞻，要求 `@` 前是空白或行首：

```java
// 修复前
Pattern.compile("@(\\S+)");

// 修复后
Pattern.compile("(?<!\\S)@(\\S+)");
```

`git@github` → `@` 前是 `t`（非空白）→ 不匹配 ✅
` @src/main/Foo.java` → `@` 前是空格 → 匹配 ✅

#### 2.12.4 教训
- 正则匹配"语法糖"时必须有足够的前后文约束，否则容易误判
- 用户输入中的 `@` 存在于 Git URL、邮箱等常见场景中

### 2.20 并发工具调用确认框输出穿插

#### 2.20.1 问题场景
AI 同时执行 2 个 exec 命令，确认对话框输出互相穿插：

```
[!] 工具调用确认       [!] 工具调用确认
工具: exec             工具: exec
参数: {command=dir ...  参数: {command=dir ...
原因: Shell ...        原因: Shell ...
[1] 允许 [2] ...       [1] 允许 [2] ...
```

两套确认文本交错在一起，不可读。

#### 2.20.2 根因分析
`AgentRunner` 并行执行工具（`CompletableFuture.runAsync`），两个 exec 同时调用 `PermissionManager.check()` → `interactiveHandler.requestConfirmation()`。`System.out.println()` 不是线程安全的，多线程输出自然穿插。

#### 2.20.3 解决方案

```java
final Object confirmLock = new Object();
registry.getPermissionManager().setInteractiveHandler((tool, params, reason) -> {
    if (trusted.get()) return true;  // 无锁快速路径
    synchronized (confirmLock) {
        if (trusted.get()) return true;  // 双重检查
        // ... 弹框 + 等待输入 ...
    }
});
```

#### 2.20.4 教训
- 所有涉及终端输出的回调都要考虑并发场景
- `System.out.println()` 非线程安全，并行工具调用需要输出互斥
- 双重检查锁定：锁外检查优化性能，锁内再查防竞态

### 2.21 重新生成答案 — `getMessages()` 拷贝陷阱

#### 2.21.1 问题场景
Web 端点击历史 bot 消息的 🔄，后端裁剪不生效 —— LLM 仍能看到后面的对话内容，新回复中出现被裁剪掉的话题。

#### 2.21.2 根因分析
`TurnContext.getMessages()` 返回的是 `new ArrayList<>(messages)`（防御性拷贝）。`RestoreState` 在这个拷贝上调用 `remove()` 裁剪，但原列表纹丝不动。下个状态再调 `getMessages()` 又拿到完整列表。

```java
// TurnContext.java
public List<Map<String, Object>> getMessages() {
    return new ArrayList<>(messages);  // ← 拷贝！
}

// RestoreState.java（修复前）
List<Map<String, Object>> msgs = ctx.getMessages();  // 拿的是拷贝
msgs.remove(msgs.size() - 1);  // 删的是拷贝 → 原 list 不受影响
```

此后每一个状态都拿到"全新拷贝"的完整消息列表，裁剪形同虚设。

#### 2.21.3 解决方案
新增 `trimMessagesFrom(int index)` 方法直接操作内部列表：

```java
// TurnContext.java
public void trimMessagesFrom(int index) {
    while (messages.size() > index) messages.remove(messages.size() - 1);
}

// RestoreState.java（修复后）
ctx.trimMessagesFrom(idx);  // 直接改内部 list
```

非 Number 的情况（boolean 向后兼容）也走同一条路径。

#### 2.21.4 教训
- "防御性拷贝"的 getter 模式在**读后即改**场景下是陷阱 —— 看起来拿到了数据，实际改的是废纸
- 需要同时提供"直接修改"的 API（如 `trimMessagesFrom`），调用方明确知道自己在改内部状态
- 单测应该验证"getter → 修改 → 再次 getter 确认修改生效"

### 2.22 CLI 突然退出（干着干着退回 shell）

> 时间：2026-08-07
> 用户报：CLI 用着用着毫无征兆退回 shell 提示符。用户确认此 bug **早于命令系统重构就已存在**。

#### 2.22.1 问题场景
CLI 运行过程中突然退出，回到 shell 提示符，无报错无堆栈。用户反馈"干着干着突然退出了，比如：S function to index.html...（AI 回复打印到一半）"。

#### 2.22.2 根因分析
三个叠加根因，都集中在 `CliChannel` 的输入处理：

1. **`Scanner.close()` 关闭了 `System.in`**（致命）：
   ```java
   // 修复前 readLine() 的 catch 分支
   try { scanner.close(); } catch (Exception ignored) {}
   // Scanner.close() 会连带关闭底层 System.in
   // → 之后 hasNextLine() 永远返回 false → runInputLoop break → CLI 静默退出
   ```
2. **默认 REPORT 解码器抛 `MalformedInputException`**：`new Scanner(System.in)` 用默认解码器，遇到粘贴含 emoji/特殊 Unicode 的字节时抛 `MalformedInputException`。它不是 `RuntimeException`，`readLine()` 的 catch 接不住，直接传播崩溃。
3. **JLine 竞争假 EOF**：CancelMonitor 与 LineReader 并发读同一个 `terminal.reader()`（JLine `NonBlockingReader` 非线程安全），导致 LineReader 读到假 EOF 抛 `EndOfFileException` → CLI 退出。

#### 2.22.3 解决方案
```java
// ① 绝不 close scanner —— 只重建（重建 new Scanner 不会影响 System.in）
private String readLine() {
    synchronized (scanner) {
        try { return scanner.nextLine(); }
        catch (RuntimeException e) {
            logger.warn("Scanner 异常，重建: {}", e.toString());
            scanner = createUtf8Scanner();   // 替换而非 close
            return "";
        }
    }
}

// ② REPLACE 解码器 —— 坏字节替换为 � 而不是抛异常
CharsetDecoder decoder = charset.newDecoder()
        .onMalformedInput(CodingErrorAction.REPLACE)
        .onUnmappableCharacter(CodingErrorAction.REPLACE);
return new Scanner(new InputStreamReader(System.in, decoder));

// ③ 主循环兜底 —— 任何异常记录并继续，不退出
while (running) {
    try {
        // ... 整段 while 体 ...
    } catch (Exception e) {
        logger.error("CLI 主循环异常（继续运行）: {}", e.toString());
    }
}

// ④ 流式结束后 join CancelMonitor，避免它仍阻塞在 reader 上竞争假 EOF
stopCancelMonitor();  // join(300)
```
同时 `readCliLine()` 捕获 `EndOfFileException`（Ctrl+D 真 EOF → 退出）与 `UserInterruptException`（Ctrl+C → 忽略），其他异常**重建 LineReader 而非降级 Scanner**（避免 JLine 原生终端下 System.in 不可用）。

#### 2.22.4 教训
- **`Scanner.close()` 会关闭底层流** —— 共享 System.in 时绝不可 close，只能重建
- 编码解码器的异常策略必须显式设置，默认 REPORT 在用户输入不可控时是炸弹
- JLine 的 `NonBlockingReader` 非线程安全，多个读者必须互斥或串行
- 新增 CLI 日志落盘（`logs/nanobot-cli.log`，WARN+），异常可追溯

### 2.23 权限确认 dialog 被 thinking spinner 覆盖

#### 2.23.1 问题场景
工具权限确认提示行被 thinking spinner 覆盖：
```
原因: Shell 命令执行需要您的确认
  / Thinking... 后都放行 [3] 拒绝    ← spinner 的 \r 刷掉了 [1] 允许 [2]
```

#### 2.23.2 根因分析
spinner 线程用 `\r...\r` 循环刷屏，dialog 线程打印确认提示，**两个线程竞争 System.out**。spinner 不感知 dialogActive，持续用 `\r` 回行覆盖，把 dialog 刚打印的提示行冲掉。

#### 2.23.3 解决方案
`beginDialog()`/`endDialog()` 协调 spinner 生命周期：

```java
private void beginDialog() {
    dialogActive = true;
    stopThinking();            // 置 thinking=false
    Thread t = thinkingThread;
    thinkingThread = null;
    if (t != null) { try { t.join(200); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } }
}   // join 等待 spinner 清行完成，不再覆盖提示

private void endDialog() {
    dialogActive = false;
    if (currentRequestId != null && !cancelled) startThinkingSpinner();  // 流式还在则恢复
}

// spinner 循环里也要感知 dialogActive
while (thinking) {
    if (dialogActive) { Thread.sleep(50); continue; }  // dialog 期间不刷屏
    System.out.print("\r  " + dim(frames[i] + " Thinking...") + " \r");
    ...
}
```

#### 2.23.4 教训
- 任何两个线程都竞争 `System.out` 的终端场景，都要有明确的输出所有权交接
- spinner 这类循环刷屏组件必须感知"暂停"状态，不能只依赖外部 stop

### 2.24 CMD 下选确认后误报 [已中断]

#### 2.24.1 问题场景
CMD（无终端，降级 Scanner）下权限确认选 "2"（信任）后，立即提示 `[已中断]`，但 AI 回复还在继续（还在 thinking）。

#### 2.24.2 根因分析
CancelMonitor 有两个分支：JLine 分支（`terminal != null`）**已检查 `dialogActive`**；但 `System.in` 分支（CMD）**没有**。CMD 下 `readInteractiveLine()` 也从 System.in 读，用户确认输入 "2" 一进缓冲，`System.in.available() > 0` 立即成立 → CancelMonitor 把它当作中断信号消费掉 → `cancelled=true` → 主线程打印 `[已中断]`。而 AgentLoop 的 turn 根本没被中断，spinner 继续转。

```java
// 修复前（CMD 分支）
while (currentRequestId != null && !cancelled) {
    if (System.in.available() > 0) {   // ← 用户输入的 "2" 命中这里
        readLine();
        cancelled = true;
        currentRequestId = null;        // → [已中断]
        break;
    }
    Thread.sleep(200);
}
```

#### 2.24.3 解决方案
给 `System.in` 分支补上 `dialogActive` 检查，与 JLine 分支对齐：

```java
while (currentRequestId != null && !cancelled) {
    // dialog 期间必须跳过：确认提示的输入（如 "2"）不能当作中断信号
    if (dialogActive) { Thread.sleep(100); continue; }
    if (System.in.available() > 0) { ... }
}
```

#### 2.24.4 教训
- CancelMonitor 有**两套实现**（JLine / System.in），修一处必须同步另一处
- "任意输入即中断"的策略太激进，dialog 期间输入归属权必须显式划分
- 排查 "bug 只在一个平台/分支出现" 时，优先找分支间行为不一致的地方

### 2.25 `/resume` 切会话后首条消息卡死

#### 2.25.1 问题场景
`/resume cli_1786071025560` 切换会话后，发第一条消息，spinner 一直转，永不返回。日志无异常（最后一条是切换前的启动日志）。

#### 2.25.2 根因分析
订阅 key 与发布 key **错位**。AgentLoop 发布 outbound 时用 `message.getSessionId()`（**裸** sessionId，`CliChannel.sendMessage` 传的就是裸 id），Dispatcher 按裸 id 路由到 `sessionSubscribers`。但切会话回调里 `subscribeToOutbound(sessionKey)` 订阅的是**带 `cli_` 前缀**的 key：

```java
// 修复前
this.subscriberQueue = messageBus.subscribeToOutbound(sessionKey);  // cli_1786071025560 ✗
this.sessionId = sessionKey.startsWith("cli_") ? sessionKey.substring(4) : sessionKey;  // 1786071025560

// 路由链
// AgentLoop.sendResponse → messageBus.publishToOutboundQueue(msg)
// Dispatcher: sessionSubscribers.get(msg.getSessionId())  → 裸 "1786071025560"
// 订阅注册在 "cli_1786071025560" → 匹配不到 → 流式事件全丢
```

`currentRequestId` 永远等不到 `isStreamEnd()` → `waitForStreamCompletion()` 死等 300 秒。初始会话正常是因为启动时 `subscribeToOutbound(sessionId)` 用的就是裸 id。

#### 2.25.3 解决方案
先还原裸 sessionId，再订阅：

```java
String channelPrefix = "cli_";
String newSessionId = sessionKey.startsWith(channelPrefix)
        ? sessionKey.substring(channelPrefix.length())
        : sessionKey;
BlockingQueue<OutboundMessage> oldQueue = this.subscriberQueue;
this.subscriberQueue = messageBus.subscribeToOutbound(newSessionId);  // 裸 id，与发布 key 对齐
if (oldQueue != null) messageBus.unsubscribeFromOutbound(this.sessionId, oldQueue);
this.sessionId = newSessionId;
```

历史加载链路本身正确（`cli:xxx` → SessionStore 消毒成 `cli_xxx` 目录，与 `/resume` 列表 key 一致），无需改动。`consumerThread` 每次循环 snapshot 读 `volatile subscriberQueue`，切会话后自动换新队列。

#### 2.25.4 教训
- **订阅 key 必须与发布 key 精确一致** —— 路由类 bug 表现是"卡死"而非报错，最难排查
- "卡死无日志"是路由错位 / 事件丢失的典型信号，不是代码死循环
- safe key（目录名 `cli_xxx`）、逻辑 key（`cli:xxx`）、路由 key（裸 `sessionId`）是三个不同概念，混用必踩坑

### 2.26 权限确认框无超时 — 等待用户输入的"永久假死"盲区

#### 2.26.1 问题场景
CLI 调用需授权的工具（`exec` 等）时弹出权限确认框（`[1]允许 [2]放行 [3]拒绝`），
若用户离开终端 / 终端失联 / 忘记响应，**确认框会无限等待用户输入，整轮对话永久卡死**。
`ask_user` 工具对话框同理。排查超时栈时发现：主循环/流式/LLM/工具执行**全都有超时**，
唯独"等用户输入"这一环没有任何总超时——这是最隐蔽的假死源。

#### 2.26.2 根因分析
`CliChannel.readInteractiveLine()` 两个分支都无总超时：
- **JLine 分支**：`reader.read(200)` 逐字符读，`while(true)` 无限循环——单次读取有 200ms 超时，但**没有总 deadline**；
- **CMD/无终端分支**：直接 `readLine()` → `scanner.nextLine()`，这是**真正无限阻塞**、无法中断。

结果是：用户不输入 → 确认框永久等待 → 持有 `terminalLock` → CancelMonitor 也让路 → 整个 CLI 停摆。
设计上"等待人输入"被认为天然安全（人会回来），但人可能离开/失联，必须和等待外部服务一样设超时。

#### 2.26.3 解决方案
给 `readInteractiveLine` 加总超时参数，**300s 无输入自动拒绝/跳过**，两个分支统一加 deadline：

```java
private String readInteractiveLine(int timeoutSec) {
    long deadline = timeoutSec > 0 ? System.currentTimeMillis() + timeoutSec * 1000L : Long.MAX_VALUE;
    synchronized (terminalLock) {
        if (terminal == null) {
            // CMD/无终端：scanner.nextLine() 无法中断，改用 System.in 轮询 + deadline
            while (System.currentTimeMillis() < deadline) {
                if (System.in.available() > 0) { int ch = System.in.read(); ... }
                else Thread.sleep(50);
            }
            if (buf.size() == 0) return null; // 超时 → 调用方按拒绝处理
        }
        // JLine：reader.read(200) 本就非阻塞，循环内检查 deadline
        while (System.currentTimeMillis() < deadline) { int ch = reader.read(200); ... }
        if (sb.length() == 0) return null;
    }
}
```

调用方各自兜底，保证超时后**能回到对话**：
- 权限确认框（`setupInteractivePermission`）：返回 `null` → 打印"等待确认超时，已自动拒绝" → `return false` → `PermissionManager` 返回 `denied("用户取消了操作")` → LLM 收到拒绝原因继续作答；
- `ask_user`（`setupAskUserHandler`）：返回占位文本 `"（用户等待超时未回答）"`，LLM 感知"用户没回答"而非空串被当成"已回答"。

#### 2.26.4 教训
- **凡是等待人的输入，也要设超时** —— 用户可能离开、终端可能失联，Agent 不能因此永久停摆
- 排查"永久假死"时，超时栈要**逐层过一遍**：主循环→流式→LLM→工具→进程→交互，漏掉哪一环都可能致命
- CMD 降级路径（Scanner 无限阻塞）是超时兜底最容易遗漏的分支——现代终端走 JLine，但 CMD 下体验差还容易假死，必须单独处理

### 2.27 配置链路断链 — setter 存在但无人调用，改配置不生效

#### 2.27.1 问题场景
用户要求"工具执行统一超时做成可配置"，检查 `AgentRunner` 时发现：
`setMaxToolResultChars()` / `setToolHintMaxLength()` setter 都已存在，
`Config.AgentDefaults` 里也有对应字段（默认 16000 / 40），
但 grep 全项目发现 **setter 没有任何调用方** —— 配置里改这些值根本不生效。

#### 2.27.2 根因分析
这是典型的**"写了接口没接链路"**：setter 是给外部注入用的，但 `AgentLoop` 构造 runner 后
只调用了 `setHookManager()`，没有把 `AgentDefaults` 的工具级配置注入进去。
`AgentRunner` 内部的 `maxToolResultChars = 16_000`、`toolTimeoutSeconds = 90` 都是**硬编码默认值**，
配置字段只是"看起来可配"，实际是死配置。

#### 2.27.3 解决方案
在 `AgentLoop` 构造 runner 后统一注入四个工具级配置（修复断链，同时新增超时两个字段）：

```java
this.runner = new AgentRunner(provider, registry, messageBus);
Config.AgentDefaults defaults = config.getAgents().getDefaults();
this.runner.setMaxToolResultChars(defaults.getMaxToolResultChars());
this.runner.setToolHintMaxLength(defaults.getToolHintMaxLength());
this.runner.setToolTimeoutSeconds(defaults.getToolTimeoutSeconds());   // 新增
this.runner.setMaxToolRetries(defaults.getMaxToolRetries());           // 新增
```

同时 `AgentDefaults` 新增 `toolTimeoutSeconds`（默认 90）/ `maxToolRetries`（默认 3）字段，
`AgentRunner` 补 `setToolTimeoutSeconds()` / `setMaxToolRetries()` setter。

#### 2.27.4 教训
- **写配置/防御代码时，要检查生效链路** —— 光有 setter、配置字段、默认值不算数，得有地方真正调用它
- 排查"配置不生效"先 grep setter 的调用方，再 grep 字段的读取点，两步定位断点
- 兜底机制的价值在于"真实接上"——孤立的防御代码（未被调用的超时、未注入的配置）等于没有
